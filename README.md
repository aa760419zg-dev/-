# 我們的家

夫妻共用家庭管理 PWA 的第一版操作原型。繁體中文、iPhone 響應式介面。

## 執行

需要 Node.js 22 以上，使用 Supabase SDK，建置時需要 esbuild。

```sh
cd /workspace/-
npm ci --cache /tmp/our-home-npm-cache
npm start
```

預設 3000 埠，可用 `PORT` 指定。`npm test` 驗證帳戶計算；`npm run check` 驗證 JS 語法。

## 手機版導覽與同步

小於 760px 使用單行頁面標題（首頁為目前月份）及同步圓點；已同步為綠，離線、同步中或更新排隊時為灰。桌機保留左側選單、標題與新增按鈕。登出及目前成員暱稱移至設定，不放在每頁頂部。

手機底部分頁固定為首頁、帳本、寵物、家務、更多；更多面板包含運動健康、操作紀錄、設定。分頁與儲存區保留 safe-area 底部空間，分頁點擊區至少 60px、文字 11px。浮動新增按鈕在分頁上方：首頁沿用月曆選取日；寵物依列表／個別寵物目前分頁開啟對應表單。手機表單為底部面板，可從頂部標題列向下滑或點背景關閉；儲存中不允許用這些方式關閉。桌機不顯示浮動按鈕。

帳本與運動健康月份使用左右箭頭。手機帳本以一張卡整合餘額與本月收支；沒有資料的區塊合併提示。用藥與 Apple Watch 等補充說明透過 ⓘ 開啟，腳印／掃把圖示用於寵物／家務。

收到 Realtime、回前景或輪詢更新時，任何 input／select／textarea／可編輯元素有焦點，或表單、選單面板仍開啟，就先排隊。失焦後再次檢查焦點再同步；即使 RPC 已開始，回應期間取得焦點也不套用或重繪。這避免搜尋／中文選字／鍵盤被更新打斷。

新增測試覆蓋 375px 五格分頁、各頁浮動新增、日期帶入、面板關閉、月份切換與輸入焦點保護。另用 Chromium 在 375px 驗證月曆寬度不超過視窗、日期格高 52px、分頁與浮動按鈕不重疊，並在 1280px 驗證左側選單保留。這不取代 iPhone 實機鍵盤與安全區驗證。本次調整不需要新的資料庫 SQL。

手機首頁順序為今日待辦、月曆、所選日期清單；待辦不隨所選日期改變，預設最多顯示三項，其餘可展開。搜尋移到頂部，圖例收進月曆標題的 ⓘ，金額摘要放在月份下方。篩選採 32px 膠囊、44px 觸控區，全部時只有「全部」實心，選個別類別則顯示相應色點。

手機帳本依日期分組，點整列編輯；說明顯示大分類 › 子分類及付款方式，成員色點來自 members。刪除移到編輯面板底部，保留確認與五秒復原。手機與桌機使用相同的新版記帳表單，桌機以置中對話框呈現。

寵物個別頁返回與資料選單移到頂部，頭像／名字／種類一行，疫苗驅蟲標籤縮短。家務手機列表精簡為圖示、到期／上次完成者、圓形完成按鈕，點列開詳細面板；置頂／編輯／刪除在面板內。新增／編輯可選八種圖示，未指定時依名稱自動選取，不強制重寫舊家務。桌機列表及表單保留原有結構。

列表與說明的日期統一由 `dates.js` 格式化：今天／昨天／明天、今年 M/D（星期）、其他年份 YYYY/M/D。原始 JSON、資料 ID 與 type=date 輸入值仍是 ISO 日期。浮動新增在向下捲動時縮小並半透明，向上恢復；頁面底部預留按鈕、分頁與安全區空間。

## 已支援

- 共同帳戶基準餘額、補款、支出、個人支付、月度分類與低餘額提示。帳本支援可管理的大分類／子分類、最近使用與固定收支。內建簡易計算機，支援四則與括號、精確小數運算，結果四捨五入至小數 2 位，可帶入記帳金額；計算本身不會存入帳本。
- 首頁家庭紀錄月曆：週一起算、左右切月／手機滑動、分類篩選（本機記憶）、關鍵字搜尋及當日清單。收支、寵物、家務完成日、運動以實心圓點呈現；家務／預防針／回診預定以空心圓點呈現。
- 今日待辦不受分類篩選影響，提供餵藥、到期家務、逾期及 7 天內預防針提醒與到期回診。今日待辦中的安排不在當日清單重複列出；完成後顯示實際紀錄。
- 寵物新增先選寵物與專用紀錄類型，帶入選定日期；餵藥從該日用藥時段選取，禁止預先標記未來餵藥。
- 回診可完成／取消：完成時新增就診（可同步帳本），並在同一次存檔結束舊提醒。刪除該次回診會重新開啟來源提醒，還原可一併復原。預防針依同寵物、同項目的最新施打紀錄提醒，舊提醒自動被取代，也可手動取消。
- 搜尋標示已記錄／預定／已逾期與類別；寵物和家務紀錄連結會定位並標示對應項目。封存行程的操作歷史仍可查看，但不能還原。
- 共同行程及休假入口已移除，`#calendar` 導向首頁。舊 `events` 不呈現、不改寫，備份匯出仍完整包含；匯入也保留目前封存行程。
- 各寵物飲食、觀察、體重、餵藥、就診紀錄與飲食複製。
- 家務支援每 N 天／週／個月與兩種排程：新項目預設「從完成日起算」，下次日期為實際完成日加週期；「固定日期」沿原 anchor／next 排程，保留固定星期或月日。既有項目首次載入會經 retryMutation 寫入排程方式與操作紀錄：週為固定日期，其他為從完成日起算；不變更原 next 或舊 history。
- 家務清單合併為一張卡，置頂優先後依到期日排序，逾期紅色、三天內黃色、正常綠色。空白家庭可一鍵加入濾心90天、冷氣濾網30天、床單14天、澆花3天、掃地7天、貓砂1天，全部從完成日起算。
- 完成家務直接存檔、不跳確認，五秒內可復原下次日期、上次完成日及整份 history；復原也會留下操作紀錄。新 history 為 `{date,userId,name}`，讀取時從 members 解析現有暱稱，舊日期字串保留並顯示完成者未知。點家務名稱可看完整完成歷史。
- 完成日起算範例：14天項目原定10/1，10/20完成後為11/3；90天項目原定12/31，2026/10/28提早完成後為2027/1/26。固定月日遇短月用月底、之後恢復 anchor 月日；從完成日起算則以實際完成日計算。無手機推播。
- 阿嘎／糖糖可自行新增、編輯每日多筆運動（名稱、日期、分鐘、開始時間）。
- Apple Watch 單次訓練數據手動紀錄：動態熱量、總熱量、平均心率、距離、主觀強度及備註；不直接讀取 Apple 健康。
- 運動月曆、按日期查詢、月度天數／次數／時間／已填動態熱量統計；InBody 紀錄及全期趨勢。
- Email 註冊登入、家庭邀請、雲端存檔與同步、JSON 匯出還原、Web App manifest（需先完成下列後台設定）。

## Supabase 設定（尚待使用者執行）

1. 在自己的 Supabase 專案 SQL Editor 新建查詢，貼上並執行 `supabase/setup.sql` 全文。腳本可重複執行，不刪除現有資料。先在本機 PostgreSQL 相容引擎驗證，並非已在遠端執行。
2. Authentication 的 Email 登入及 Confirm email 須啟用。正式部署後在 URL Configuration 將 Site URL 設為部署的 HTTPS 網址，Redirect URLs 加入相同網址。確認信將導向該網站，勿使用 localhost 作為手機登入網址。
3. public/config.js 已設定使用者提供的 Project URL 與 Publishable key；它們可在瀏覽器公開。禁止使用 secret/service_role。
4. 使用 App 的建立帳號功能，兩人各用自己的 Email，收信驗證後登入。
5. 一人建立家庭，在帳戶設定填入另一半的 Email 並儲存邀請。不會自動寄邀請信，請自行告知對方。對方登入後按「接受另一半的邀請」。不要各自建立不同家庭。
6. 登入後家務、收支、行程、寵物與健康資料儲存在同一家庭的雲端文件。使用 Realtime Broadcast 通知更新；編輯視窗開啟時延後至關閉才載入。回到前景立即同步，60 秒輪詢作備援，手動重新同步位於設定頁。

## 權限與一致性

資料表已啟用 RLS，且撤銷 anon/authenticated 的直接存取權。只允許已登入使用者透過 RPC 操作，RPC 以 auth.uid() 驗證家庭成員。家庭最多兩人，邀請以登入權杖的已驗證 Email 對應。必須保持 Email confirmation 啟用。

存檔比對 revision；衝突後重讀最新文件，再重做同一個以 ID 查找紀錄的修改，初次嘗試外最多重試 3 次。耗盡時仍保留最新 revision，下一次操作不會卡在舊版本。非衝突錯誤不自動重試。網路失敗不會顯示存檔成功。成員依 userId 對應 document.members，暱稱與代表色可自行修改，舊紀錄以 personUserId 保留身分對應。家庭雙方皆可編輯，無私人紀錄。

## 驗證與限制

`npm test` 包含帳戶計算、備份、模擬登入 UI 及本機 PostgreSQL 相容引擎的匿名拒絕、成員隔離、邀請、家庭容量、版本衝突測試。這不等於遠端 Supabase 或 iPhone 實機測試。

既有正式網址為 https://our-family-home.vercel.app/ 。本次 Realtime 與成員遷移已做本機測試，遠端 SQL 升級與雙手機通知仍需實際驗證。無銀行串接、推播或離線快取。密碼重設 UI 尚待實作，管理員可先透過 Supabase 處理。InBody 不提供醫療診斷。舊版 `our-home-v1` 本機資料保留，未自動上傳；舊備份可登入後匯入，匯入會取代家庭所有資料，請先備份。

部署時先 `npm ci && npm run build`，將 public 目錄託管至 HTTPS 靜態網站，或在 HTTPS 反向代理後執行本服務。Safari 分享選單 → 加入主畫面。正式 iOS 品質驗證仍需實機，包含加入主畫面與 Safari 防縮放體驗。已備有 180／192／512 PNG 圖示；來源為 icon.svg，可用 scripts/generate-icons.py（需要 Pillow）重建。

## 多寵物健康管理

- 多寵物個人資料（名字、種類、品種、生日、性別、結紮、晶片、照片）。獨立網址如 `#pets/<id>/weight`，可直接返回指定毛孩的分頁。
- 體重到 0.01 kg，歷史清單、折線圖與總覽最新體重。既有飲食紀錄依名字保留對應；可確定單位的舊體重資料會轉入體重頁。
- 用藥計畫：每天 N 次或每 N 天一次、開始及結束日。每天時段可命名（slotNames），預設1次早上、2次早上／晚上、3次早上／中午／晚上、4次以上第N次；舊計畫不需改寫也有預設名稱。新餵藥紀錄保存 slotName 快照，之後編輯標籤不改寫歷史，槽位 ID 仍是 planId:日期:序號。今日清單出現在首頁及寵物頁；餵藥快照保留藥名、劑量、實際登入者 ID、由 members 對應的暱稱與時間。勾選前重讀雲端，固定槽位 ID 加上 revision CAS 防止並行重複存檔。這是記錄已餵藥，不是實際給藥鎖；兩人仍需溝通避免在尚未勾選時各自餵藥。失敗或網路不明時應先重新同步檢查。
- 已有餵藥紀錄的計畫不能變更劑量或頻率，應停用後新增，原紀錄保留。
- 就診原因、診斷、醫囑、費用及照片；勾選同步帳本會與就診在同一次 revision 寫入，重存更新同一筆支出。取消同步會移除連結支出。
- 預防針／驅蟲：施打與下次日期，7 天內及逾期顯示於首頁。新的同項目施打紀錄取代舊提醒。

### 照片需要一次後台設定

在 Supabase SQL Editor 執行 `supabase/pet-storage.sql`，建立私人 bucket 與家庭成員存取政策。腳本不更動家庭紀錄，可重跑。**尚未代替使用者在遠端執行**。其他新寵物功能沿用既有 JSON 文件，不需要更改資料表。

照片接受 JPEG/PNG/WebP，原始單檔上限 15 MB，瀏覽器壓縮至最長邊 1600px 的 JPEG，每次就診可新增最多 4 張，儲存單檔上限 5 MB。需保留原始報告，縮圖不取代醫療原件。簽名連結有效 10 分鐘；無公開 bucket。JSON 匯出只備份照片路徑，不含圖片本身，照片需另外在 Supabase 備份。無法確認文件寫入結果時保留上傳檔，可能有未引用檔案，避免誤刪已成功儲存的照片。

測試使用本機 PostgreSQL 相容引擎驗證成員政策與並行存檔拒絕，以及模擬照片上傳的 UI 測試；真實 Supabase Storage、手機選照片／壓縮、雙帳號實機驗證仍需在後台設定完成後執行。

## 本次升級：衝突重試、即時更新與成員身分

既有 Supabase 專案需在 SQL Editor 執行 `supabase/member-upgrade.sql`。它只升級 family_read，不刪除表或紀錄；首次載入依 family_members 補齊 document.members（owner 初始阿嘎，其餘糖糖），已有暱稱與顏色不覆寫。create/join 原本會呼叫 family_read，因此新建／加入也會寫入成員。全新安裝使用已更新的 setup.sql 即可。尚未代替使用者在遠端執行此腳本。

未升級 SQL 的舊伺服器有相容路徑：目前使用者首次登入時補上自己的 members 資料並用 revision 存檔；另一位須登入才會補上。完整名冊與首次載入一次補齊兩位需套用上述 SQL。

`mutations.js` 處理版本衝突，不重送舊文件。所有操作在 callback 內透過最新根文件按 ID 查找；新增資料使用固定 ID，家務完成檢查原排程是否已完成，用藥每個槽位有固定 ID。若重試發現別人已餵藥，顯示「已由 X 標記餵藥」並停止。

`realtime.js` 訂閱 `home:<家庭ID>`，儲存成功只發送 `revision` 事件與 `{revision}`，不廣播資料。另一端僅在收到較新版本後，透過受權限保護的 family_read 讀取；任一編輯 dialog 開啟或正在存檔時延後，關閉後合併處理通知。切換家庭與登出移除頻道。頻道重連、App 回前景及每 60 秒備援可補回漏訊；通知發送失敗不把已成功的存檔誤報為失敗。Broadcast 是僅含版本的公開 topic；不承載家庭資料，實際資料仍由 RPC 成員授權保護。

設定頁修改自己的暱稱及顏色。記帳、休假、健康預設目前登入者；餵藥與就診以登入者 userId 查 members，不以 owner 身分推算暱稱。owner 僅用於舊資料遷移及邀請管理權限。

## 操作紀錄、刪除及還原

所有 App 業務修改經既有 mutate/retryMutation。在同一個重試 callback 中先取快照、套用修改，再依各集合的穩定 ID 產生 activity；將不含 activity 的文件與本次紀錄分別作為 `family_save` 的 `new_document`、`new_activity` 傳送，在同一筆資料庫交易中儲存。操作 ID 與時間在重試外產生，重試時丟棄失敗快照、重新比較最新資料，避免重複紀錄。操作者從 document.members 依 userId 取得，保留操作當時暱稱。

設定頁 → 操作紀錄，可依成員／類別篩選、查看僅變更的欄位。在獨立的 `family_activity` 表保留最近 24 個月，無 2000 筆上限；列表每頁 50 筆，捲到底自動載入（也可按載入更多），篩選由伺服器執行。帳戶設定、暱稱、家務完成／置頂、停藥、餵藥、休假、就診同步帳本以及備份匯入均納入。匯入不覆蓋資料表中的操作紀錄，也不接受備份歷史覆蓋；匯入快照不包含 activity 本身，避免遞迴膨脹。

每次連動修改共用 groupId。主操作保留 changes（每個集合的 ID、完整前後值與原始位置），寵物刪除的 before 另包含寵物及所有相關紀錄。還原任何一筆連動操作會恢復整組（例如就診與帳本、用藥與餵藥），以維持資料一致；同 ID 不會重複加入。每次真正還原都記錄「還原」，已還原或取消不新增假紀錄。若資料或後續操作紀錄顯示已有較新修改，先警告並確認，再允許覆寫；衝突重試期間也重新檢查。

刪除前列出內容；刪除寵物列相關筆數，刪除有餵藥紀錄的計畫提示改用停用。刪除後提供 5 秒復原提示，逾時仍可從操作紀錄還原。照片只移除資料中的引用，保留雲端檔案供還原，包含編輯時換掉的舊照片；請依實際儲存用量另做人工保留政策。

未來私人行程的操作紀錄會依 before/after 的 visibility 與 ownerId 過濾，非本人不顯示；連動快照或匯入若包含他人的私人行程也不顯示。這是操作紀錄 UI 的前置過濾，單一家庭 JSON 仍可由家庭成員讀取，並非完整私人資料授權方案。

## 操作紀錄資料表升級（activity.sql，使用者已確認執行）

執行順序：

既有正式環境使用者已確認執行成功；以下供新環境或重建時參考。本次家務／用藥調整不需新的 SQL。

1. 先部署包含 `public/activity-store.js` 的新版前端，讓兩支手機重新整理。資料庫仍是舊版時，前端會在送出存檔的當下使用舊協定保存操作紀錄；記憶體內的家庭 document 已不再包含 activity。
2. 確認 `supabase/history.sql` v2 已執行（本專案使用者已確認）。
3. 既有環境不用重跑 `setup.sql`。到 Supabase → SQL Editor → New，貼上 **完整的 `supabase/activity.sql`**，按 Run。成功後目前資料中的 activity 會一次性搬到 `family_activity`，原文件移除此欄位並遞增 revision。可重複執行，不會重複搬移或刪除帳本／寵物等資料。
4. 兩支手機再次重新整理；新增一筆紀錄並進設定 → 操作紀錄確認可見。仍開著的舊版 App 送來含 activity 的文件，也會由新版 family_save 原子地搬入資料表，不會把活動歷史放回文件。

遷移與存檔都會鎖定家庭資料列，revision 檢查成功後才提交文件與操作紀錄；紀錄驗證失敗也會整筆回滾。新紀錄每次最多 100 筆，舊文件中既有的 activity 不受這個批次上限限制。相同 id 使用 `on conflict do nothing` 去重。伺服器在寫入時清理該家庭 24 個月以前的紀錄；讀取也排除已到期紀錄。一般成員與匿名角色沒有表的直接讀寫權限，只能透過限本家庭的 list/get RPC 讀取。

分頁以 `(at, id)` 倒序，除了要求的 before_at 參數，增加可選的 `before_id` 游標，避免相同時間戳記跨頁漏紀錄。還原會取得原操作的完整 root 紀錄，查詢它之後的活動；每次衝突重試前都重新查詢再確認。五秒復原提示使用剛存檔成功的記憶體快照。私人行程仍由 visibleActivity 在前端過濾；不是資料庫層的私人授權。

本機 PostgreSQL 相容測試模擬一年每天 3 筆收支、6 項每日家務都到期完成：家庭文件為 442,582 bytes（含完成者物件）（低於 500 KB），3,285 筆操作紀錄獨立保存。這是該模擬情境的結果，業務資料仍會隨使用時間增加。

匯出 JSON 現在只包含家庭業務資料，不包含獨立操作紀錄；要完整備份活動歷史須另備份 `family_activity`。舊 JSON 備份內的 activity 不覆蓋現在的操作歷史。歷史 v2 只備份業務文件，不重複儲存操作紀錄。月曆搜尋在中文組字完成後防抖 200ms，只更新結果區，不重建輸入框。

## 雲端歷史版本 v2（使用者已確認執行）

`supabase/history.sql` 保留使用者先前提供的完整 v2 SQL，使用者已確認在 Supabase 執行成功。全新環境仍須在 SQL Editor 執行；更新 GitHub／部署 App 不會自動執行資料庫 SQL。

v2 在排除 `activity` 後的資料實際變更時備份上一版，每戶保留最後 200 版。新歷史不含操作紀錄；升級也會移除既有歷史中的 `activity`，但保留版本及其他資料，且不修改目前家庭文件的 `activity`。若仍需舊歷史的操作紀錄，升級前請另存備份。只有操作紀錄變更或只增加 revision 時不產生歷史，因此歷史 revision 可以不連號。App 的 authenticated/anon 角色無法直接查閱。

此調整減少歷史表的重複內容，不會解除目前家庭文件 5 MB 的限制。

以下僅在 Supabase SQL Editor 以後台管理權限救援。先查詢，確認家庭與版本，再執行還原；不要將管理憑證放到 App。還原會遞增目前 revision，原來的目前文件也會由觸發器備份。

```sql
-- 先找要救回的版本；將 UUID 換成實際家庭 ID。
select id, home_id, revision, saved_at, saved_by
from public.family_document_history
where home_id = '00000000-0000-0000-0000-000000000000'::uuid
order by id desc;

-- 確認下方歷史 id 與家庭 id 後，還原至該歷史文件。
-- 12345 是示範的歷史 id，請換成上方查到的值。
begin;
select id from public.family_homes
where id = '00000000-0000-0000-0000-000000000000'::uuid
for update;
update public.family_homes as h
set document = case when h.document ? 'activity'
      then (history.document - 'activity')
        || jsonb_build_object('activity', h.document->'activity')
      else history.document - 'activity'
    end,
    revision = h.revision + 1
from public.family_document_history as history
where h.id = '00000000-0000-0000-0000-000000000000'::uuid
  and history.home_id = h.id
  and history.id = 12345;
commit;
```

後台救援回復歷史業務資料與 members，不修改獨立的 `family_activity` 表，也不把 activity 放回新版文件。範例的條件分支只為尚未遷移的舊文件保留其現有 activity；操作紀錄不代表被救回版本當時的狀態。請在還原前確認目標內容，並讓兩支手機關閉編輯、重新載入。此方式不經 App 的活動紀錄機制，僅供後台救援。正常使用一律從 App 還原。

PNG 圖示已改為不透明 RGB、四角滿版 #315c4c，讓 iOS 自行裁切；scripts/generate-icons.py 也同步更新。


## 新版記帳、分類與固定收支

手機以底部面板、桌機以置中對話框呈現。新增時自動開啟 App 數字鍵盤，金額不叫出系統鍵盤；四則算式顯示即時結果，按 ✓ 帶入金額並收起鍵盤。金額必須大於零。支出／收入切換保留金額和日期；備註整合原用途與補款說明，記錄人自動使用目前登入的 members 成員。支出預設記住該家庭／成員上次選擇的帳戶，收入預設共同帳戶。

分類列開啟四欄大分類與子分類選擇，含最近四個使用組合；鉛筆開啟分類管理。可新增、改名、換 emoji、排序及隱藏；改名同時更新既有收支和固定收支範本。使用中的分類需先合併才能刪除，隱藏不影響歷史顯示。統計以大分類加總，展開查看子分類，未指定子分類歸於「未分類」。

首次載入自動透過 revision 重試機制執行一次遷移，寫入一筆操作紀錄；不改舊紀錄的 kind、日期、金額或來源。financeVersion=1 避免重複遷移。原資料的 events 保持不變，備份包含 categories、recurring 與帳戶欄位。

| 舊分類／類型 | 新分類 |
| --- | --- |
| 伙食 | 支出／餐飲 |
| 寵物醫療 | 支出／寵物 › 寵物醫療 |
| 寵物 | 支出／寵物 |
| 水電瓦斯 | 支出／居家 › 水電瓦斯 |
| 與預設大分類同名 | 對應的大分類 |

舊 source=共同帳戶 對應 account=共同帳戶，個人支付對應該筆 personUserId（必要時以 members 名稱對應）。新收入使用 kind=收入，餘額與統計同時支援舊存入；只有共同帳戶的收支影響共同帳戶餘額，遷移前後餘額相同。就診連動支出使用寵物／寵物醫療及其分類 ID。

自動重複可選每天、每週、每兩週、每月、每年，以及結束日期或總次數（包含第一筆）。儲存第一筆與規則在同一次 mutate 完成。帳本月份右側 🔁 管理規則：暫停／恢復、修改未來範本、刪除規則；已產生的收支保留，單筆編輯／刪除不改規則。

App 載入、回前景與定期同步時補齊至今天的到期紀錄，日期跨日亦在下次同步處理；未開 App 時不會在背景執行。每次最多補 60 筆，超過時提示並在後續同步繼續。ID 固定為 rec:<規則ID>:<日期>，revision 衝突後重新查找，避免兩支手機重複產生；規則游標也避免單筆刪除後又被補回。每月以原起始日為基準，短月使用月底，下一個長月恢復原日。首頁月曆以空心收支圓點顯示未來預定項目。

所有分類、規則、收支變更與自動補記使用既有 mutate／retryMutation 及 family_activity；大批連動操作以一筆包含完整 changes 的紀錄保存，維持同一次存檔的完整操作歷史。此更新沿用現有 family_save API，**不需執行新的 Supabase SQL**。
